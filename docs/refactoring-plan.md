## 1. Цели

1. **Rust-ядро игр** (`mg-core` + крейт на каждую игру): правила, боты, детерминированная симуляция. Без tokio, сети и IO. Одно и то же ядро работает:
   - на сервере (нативно);
   - в браузере (WASM в Web Worker);
   - в Android-приложении (тот же WASM внутри WebView Capacitor);
   - в C#-ботах (через C ABI / P/Invoke);
   - в локальной арене ботов (Rust CLI).
2. **Игры без других людей идут локально.** Если в игре только ты и боты (включая одиночные 2048, Numbers Match, одиночные Snake и Stack Attack), она исполняется на клиенте, работает офлайн и без пинга.
3. **Android-приложение**, эквивалентное вебу. Приоритеты: компактность и плавность. APK публикуется в GitHub Releases.
4. **Production-grade код.** Без серьёзного упора в метрики и трейсы. Цель: устранить классы багов архитектурно, закрыть остальное тестами и поставить жёсткий CI-гейт.
5. **Добавить новую игру должно быть легко.** Есть генератор шаблона, общий conformance-сьют и документ для людей и агентов.
6. **Фундамент под соревнования ботов.** Seed скрыт, есть bot-SDK и локальная арена. Турниры на сервере делаются позже, отдельным проектом.

## 2. Зафиксированные решения

| Тема | Решение |
|---|---|
| Синхронизация | **Lockstep**. Сервер (авторитет) шлёт `MatchHeader` без seed, затем поток `TickFrame`: команды игроков и ботов, события мира, системные события. Раз в N тиков и на последнем тике в кадр добавляется `state_hash`. Клиенты крутят то же ядро. |
| Случайность | Есть только у авторитета, внутри `roll_world(&mut rng)`. Её результат рассылается как `WorldEvent`. У `apply_*` и `step` нет доступа к RNG на уровне типов. Реплеи не зависят от алгоритма RNG. |
| Реплей | Реплей — это тот же поток (`MatchHeader` + все `TickFrame`). Файл хранится как бинарный protobuf. Наблюдение, реконнект, «смотреть вместе» и одиночный просмотр используют один и тот же код. |
| Старые реплеи | Считаем, что их не существует. Совместимость и проверку старого формата не закладываем. |
| Протокол | Ломаем. Добавляются `protocol_version` (вместо строгого сравнения версии приложения), `request_id` с типизированными кодами ошибок, resume-токен и чистка схемы. |
| Транспорт | Только WebSocket. Сообщения всегда идут в **protobuf-JSON** (каноническое JSON-отображение), контракт описан в `.proto`. gRPC и порт 5443 удаляются. |
| Дисконнект в игре | По модели StarCraft 2: игра встаёт на паузу для всех, у каждого человека бюджет 60 с на партию. Через 20 с ожидания остальные могут выкинуть отключившегося. После возвращения 3 с обратного отсчёта. Когда бюджет кончается, игрок выбывает по правилам игры: техническое поражение в TicTacToe, смерть в Snake, уход рабочего в Stack Attack. |
| Правила | Все найденные баги правил чиним. В змейке ход становится одновременным. Каждое изменение записываем в changelog и покрываем тестом (раздел 7). |
| Читеры | Не волнуют. Результаты локальных игр никуда не отправляются. |
| Android | Capacitor + тот же Vue-фронт + WASM-ядро. Название «Mini Games», package id `xyz.braintvsminigames.app`, minSdk 24. |
| Релизы | Pages деплоится на каждый пуш в `master`. APK собирается по тегу `v*` или вручную (`workflow_dispatch`) и уходит в GitHub Release. Бинарник сервера прикладывается к релизу. Сервер деплоится скриптом вручную. |
| Деплой | Новый хост `146.103.106.44`. Сначала проверка по IP с фронтом, который отдаёт сам сервер. Потом пользователь переводит DNS `braintvsminigames.xyz`, и выпускается TLS-сертификат. |
| C#-боты | Правила из ядра через FFI. Нейросеть и обучение остаются на C#. Сеть переходит на новый WS-протокол. |
| Соревнования | В этом рефакторинге: протокол со скрытым seed, Rust bot-SDK, C#-боты через FFI, локальная арена. Серверные турниры потом. |
| Фронт | Vue 3 + Pinia + Tailwind, внешний вид прежний. Полируем мобильную вёрстку, рисуем canvas с учётом DPR, интерполируем движение, вводим бюджет размера бандла. |
| Тесты | Ядро: unit, proptest, golden-хэши (x86 и WASM). Сервер: интеграционные тесты со скриптованными WS-клиентами. Веб: Vitest. Playwright не делаем. |
| Гейт качества | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, тесты, ESLint, Prettier, `vue-tsc`. CI запускается на каждый пуш и PR. |
| Зависимости | Обновляем всё до актуальных версий. `Cargo.lock` коммитим. |
| Ресурсы сервера | Сервер почти не ест ресурсов: тикает только то, что идёт; кадр кодируется один раз на всех; горячий путь без аллокаций; ботам — бюджет и семафор; статику отдаёт nginx. Цифры снимаются через `loadgen` (раздел 4.9). |
| Документация | Коммитим AGENTS.md (CLAUDE.md ссылается на него) и `docs/`. Убираем их из `.gitignore`. |
| Аутентификация | Делаем сразу (раздел 4.8). Три способа: гость (имя, помечен «гость»), Google (отображается имя из Google), бот (ключ из конфига сервера). Серверная настройка `allow_guests` приходит клиенту в `Welcome`, в проде её, возможно, выключат. БД нет: сессия — подписанный сервером токен. |
| Адрес сервера в приложении | В настройках приложения можно указать любой адрес, включая `ws://IP`. По умолчанию пока `ws://146.103.106.44/ws`, после переключения DNS — `wss://braintvsminigames.xyz/ws`. |

## 3. Что сейчас не так (сводка аудита)

Полные отчёты аудита были в сессии. Здесь собраны находки, которые определяют план. ID используются в разделе 7.

### 3.1 Сервер: инфраструктура

| ID | Серьёзность | Суть | Чем закрывается |
|---|---|---|---|
| H1 | high | Глобальный `Mutex` броадкастера держится поверх `send().await` в очередь на 128 сообщений. Один клиент, который перестал читать, вешает весь сервер. | Актор на соединение, `try_send`, отключение медленного клиента |
| H2 | high | Реплей без метаданных вызывает `expect`, и задача соединения паникует. Клиент становится зомби. | Реплеи не исполняются на сервере, только ретранслируются; валидация заголовка |
| H3 | high | Настройки из загруженного реплея не валидируются. Поле `u32::MAX` вызывает OOM и abort процесса, `tick_interval 0` и ширина 0 вызывают панику. | Валидация настроек в ядре на любом пути (`Settings::validate` в `Game::new`) |
| H5 | high | Бот чужого типа: крестики-нолики уходят в горячий бесконечный цикл, змейка не двигается. | Тип бота привязан к игре, неподходящий тип отвергается на уровне типов |
| H6 | high | Утечка сессий: одиночные игры при дисконнекте висят вечно, TicTacToe при `LeaveLobby` тоже, Snake с ботами без людей тикает бесконечно. | Актор матча с явным жизненным циклом; правила «не осталось людей»; бюджет паузы |
| H7 | high | Гонка play-again: старая задача удаляет только что созданную сессию с тем же id. | Уникальный `match_id` на каждую партию |
| H8 | high | Кикнутый клиент «глохнет» и не может переподключиться. | Kick закрывает соединение, идентичность освобождается |
| M1 | med | Быстрый реконнект: teardown старого соединения снимает регистрацию нового. | Поколение соединения / resume-токен |
| M2 | med | Команды записываются в реплей с неверным тиком (гонка с тик-лупом). | Lockstep: тик назначает авторитет при формировании кадра |

| M5–M6 | med | Задачи реплеев никогда не завершаются; NaN в скорости вызывает панику. | Реплеи проигрываются на клиенте, сервер синхронизирует только управление |
| M7 | med | Неограниченные очереди и рост памяти; нет лимитов на чат, имена и размер сообщений. | Лимиты и rate-limit на соединение (раздел 5.4) |
| M8–M10 | med | Ошибки создания игры проглатываются, и лобби навсегда остаётся `in_game`. Хост уходит посреди игры — лобби удаляется. Replay-лобби видно в списке. | Явная машина состояний лобби + тесты переходов |
| M11 | med | Две расходящиеся системы валидации настроек; рабочая слабее. | Одна валидация в ядре |

| L* | low | Двойной disconnect, потеря pre-auth ошибок, ping не считается активностью, `unwrap` и мёртвый код, коллизии id с ботами, wall-clock в счёте Stack Attack, `println!` в логике. | Переписывание слоя; `tracing`; время только в тиках |

Качество кода: `message_handler.rs` на 1045 строк. Транспортные циклы WS и gRPC продублированы, setup каждой игры дублируется между `session.rs` и `replay.rs`. Ошибки — строки (`Result<_, String>`). Модули `games` и `lobby` зависят друг от друга по кругу. `lib.rs` и `main.rs` компилируют одно и то же дважды. Задачи не супервизируются. Тестов на сервер, сессии и реплеи нет.

### 3.2 Игры

См. раздел 7 (changelog правил). Кроме того:
- **S1.** У ботов змейки и у спавна еды общий RNG, поэтому реплей разъезжается с живой игрой.
- **T7.** Обход `HashMap`/`HashSet` определяет поведение: порядок ботов, ходы бота TicTacToe, порядок игроков.
- **`StdRng`** не стабилен между версиями `rand`.
- **Минимакс** не ограничен по узлам или времени. На поле 20×20 возможен CPU-DoS (T6), а оценка переполняет `i32` (T5).
- **Связанность.** Stack Attack использует proto-типы прямо как доменные; у всех игр `to_proto` живёт внутри состояния.

### 4.2 Ядро

Принципы:
- **Детерминизм.** Нет `HashMap`/`HashSet` в состоянии, только `Vec`, `BTreeMap` и битовые сетки. Нет float. Нет wall-clock.
- **Без паник на внешнем вводе.** Всё внешнее приходит через `Result`; `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::indexing_slicing)]` в game-крейтах (в тестах разрешено).
- **Зависимостей минимум.** Свой RNG (xoshiro256** + несмещённый `range` по методу Lemire, около 50 строк), свой каноничный хэшер (FNV-1a 64 поверх явной сериализации полей).
- **Игроки — это слоты `u8`** (порядок = порядок входа в лобби). Строковые id в ядро не попадают.

Набросок API (финализируется на этапе 1):

```rust
pub trait Game: Sized + 'static {
    type Settings: GameSettings;          // validate() + границы; невалидные настройки не создают игру
    type Command;                         // ввод игрока/бота
    type WorldEvent;                      // случайность от авторитета
    type View;                            // модель для рендера

    fn new(settings: &Self::Settings, players: &[PlayerSpec]) -> Result<Self, SetupError>;
    fn clock(&self) -> Clock;             // TurnBased | Fixed { tick_ms }
    fn input_policy(&self) -> InputPolicy;// сколько команд слота принимается за тик, размер буфера

    fn check_command(&self, slot: Slot, cmd: &Self::Command) -> Result<(), CommandError>;
    fn apply_command(&mut self, slot: Slot, cmd: &Self::Command);
    fn roll_world(&self, rng: &mut CoreRng) -> Vec<Self::WorldEvent>; // только авторитет
    fn apply_world(&mut self, ev: &Self::WorldEvent);
    fn step(&mut self);                   // один логический тик; для TurnBased — no-op
    fn drop_player(&mut self, slot: Slot);// бюджет паузы исчерпан / вышел

    fn awaiting(&self) -> Awaiting;       // Turn(slot) | Simultaneous | Nobody — расписание ботов
    fn status(&self) -> Status;           // InProgress | Finished(Outcome { per-slot score, winner, reason })
    fn view(&self, viewer: Viewer) -> Self::View;
    fn hash(&self, h: &mut StateHasher);
}

pub trait Bot<G: Game> {
    /// Детерминирован при заданном rng; ограничен бюджетом узлов (не временем), поэтому
    /// одинаково ведёт себя на сервере, в WASM и в арене.
    fn decide(&mut self, game: &G, me: Slot, rng: &mut CoreRng, budget: &mut Budget) -> Option<G::Command>;
}
```

**Порядок внутри тика** один для всех игр и закреплён в `Match`:
1. Команды слотов в порядке, в котором их принял авторитет.
2. `roll_world` → `apply_world`.
3. `step`.
4. Хэш (если тик кратен N).

`Match<G>` — общий драйвер. Он применяет `TickFrame`, ведёт лог и проверяет хэш. Используют его все: сервер, WASM-зеркало, LocalHost, арена, C#.

**Conformance-сьют** — generic-тесты, которые автоматически запускаются для каждой игры из реестра:
- Нет паник на случайных потоках команд (proptest), инварианты соблюдаются (каждая игра описывает свои).
- Невалидные настройки (границы ±1, нули, `u32::MAX`) отклоняются без аллокаций.
- Детерминизм: одинаковый лог даёт одинаковый финальный хэш. Golden-хэши хранятся в файлах и прогоняются на x86 и в WASM.
- Реплей: прогон «живой» `Match` → лог → повторный прогон даёт идентичные хэши на каждом тике.
- Боты укладываются в бюджет и всегда возвращают допустимую команду, когда ход за ними.
- Игра заканчивается за конечное число тиков при ботах-заглушках (для real-time — с лимитом в тестах).

### 4.3 Протокол v2

Принципы:
- Один `proto/`, `buf lint` в CI.
- Протокол идёт по WS в protobuf-JSON. На Rust для этого используется prost + pbjson, на TS — protobuf-es `toJson`/`fromJson`.
- Каждый клиентский запрос несёт `request_id`. Ответ — `Ack`/`Error{code, request_id}` или доменное сообщение с тем же `request_id`. Push-сообщения сервера идут без `request_id`.
- Handshake: `Hello{protocol_version, client_name, resume_token?}` → `Welcome{session_id, resume_token, server_version}` или `Error{PROTOCOL_UNSUPPORTED, min, max}`. При несовместимой версии клиент показывает «обновитесь» и **не** переподключается.
- Heartbeat: клиент шлёт ping каждые 15 с. Сервер закрывает соединение после 45 с тишины.
- Матч: `MatchStarted{MatchHeader}`, `TickFrame` (поток), `MatchCatchUp{header, frames[]}` (при входе, реконнекте и рассинхроне), `MatchEnded{outcome, replay_available}`, `ReplayFile{bytes}` по запросу.
- Клиент шлёт `Command{match_id, GameCommand}` и `Desync{tick, local_hash}`. На `Desync` сервер логирует и отвечает `MatchCatchUp`.
- Системные события внутри кадров: `Paused{slot, budget_left_ms}`, `Resumed{countdown_ms}`, `PlayerDropped{slot, reason}`, `DropVoteAvailable{slot}`.
- Реплеи «смотреть вместе»: хост загружает файл. Сервер проверяет размер (≤ 4 МБ) и заголовок, рассылает файл участникам и синхронизирует управление (`ReplayControl{play/pause/seek/speed}`). Ядро для реплеев сервер **не** запускает.
- Схема чистится:
  - один `PlayerIdentity`;
  - одна схема настроек лобби;
  - `View`-сообщения по играм (бывшие `*GameState`), которые используются **только** между WASM и UI и в файлах реплеев (кадры);
  - вероятности как целые (per-mille);
  - удаляются неиспользуемые сообщения.

Полное описание будет в `docs/protocol.md` (этап 3).

### 4.4 Сервер

Модель — **акторы без общих локов**:
- **ConnectionActor** (одна задача на сокет). Отвечает за декодирование, лимиты и rate-limit (token bucket), heartbeat. Исходящая очередь bounded; если она переполнена, клиент отключается, после чего может вернуться по resume.
- **Directory / LobbyService** (одна задача). Владеет идентичностями, сессиями и лобби, обрабатывает сообщения последовательно. Лобби — явная машина состояний `Open → Starting → InMatch → PostMatch`, у каждого перехода есть тест.
- **MatchActor** (задача на партию). Владеет `mg-host`, тикает через `tokio::time::interval` с `MissedTickBehavior::Delay`. Ботов считает в `spawn_blocking` с бюджетом узлов; если бот не уложился, делается «пустой» ход по правилам игры. Ведёт паузы и бюджеты, пишет лог, по завершении отдаёт итог в LobbyService. `match_id` уникален для каждой партии (H7).
- **Идентичность и сессии.** `Identity = Guest{name} | Google{sub, name} | Bot{key_id, name}` отделена от соединения (раздел 4.8). Resume-токен — 128-битный случайный, хранится в памяти, grace-период для присутствия в лобби 60 с.
- **Лимиты** (конфигурируемые):
  - размер WS-сообщения 64 КБ, загрузка реплея 4 МБ;
  - чат 300 символов и 5 сообщений за 5 с;
  - имя 32 символа, имя лобби 48;
  - команд в игре ≤ 30/с;
  - лобби на клиента 1, общий потолок матчей и соединений.
- **Конфиг**: `clap` + переменные окружения (`MG_*`), порт, путь к статике, лимиты, таймауты.
- **Логи**: `tracing` + `tracing-subscriber` (человекочитаемый формат, `RUST_LOG`). Метрик и трейсинга не делаем.
- **Shutdown**: SIGTERM и ctrl_c → `ServerShuttingDown` всем → прекращаем приём → ждём до 5 с → закрываем.
- **Статика**: сервер раздаёт собранный веб (`/`), WS на `/ws`.

### 4.5 Веб

- **Транспортный слой** (`src/net/`). `Transport` — интерфейс с методами `open/close/send/onMessage/onState`. Две реализации:
  - `WsTransport`: handshake на каждом open, resume, heartbeat, backoff с jitter, корреляция `request_id` с таймаутом, остановка при несовместимой версии, очередь отправки на время реконнекта.
  - `LocalTransport`: Web Worker с `mg-wasm` LocalHost. Эмулирует то же API лобби и матчей, поэтому UI не отличает онлайн от офлайна.
- **Сессия** (`src/session/`): типизированная шина событий (много подписчиков, exhaustive switch), `request()` → Promise.
- **Матч** (`src/match/`): `MatchClient` поверх `mg-wasm` MatchMirror. Применяет кадры, проверяет хэши, при расхождении шлёт `Desync`, отдаёт `View` и время тика для интерполяции. View передаётся из WASM в JS бинарно (`fromBinary`), это быстрее JSON.
- **Плагины игр** (`src/games/<id>/`):
  - `meta.ts`: название, иконка, границы игроков, типы ботов, кооператив/соревнование, раскладка ввода;
  - `Settings.vue`: форма, границы которой приходят из ядра через WASM (`settings_schema`);
  - `Board.vue`: рендерер;
  - `input.ts`: клавиши и жесты → команды.

  Регистрируются в одном реестре `src/games/registry.ts`. Все switch'и по типу игры в Home/Lobby/Game/GameOver исчезают.
- **Правила только из ядра.** Предсказание 2048 и доступность hint/refill берутся из того же WASM. Копий логики в TS нет.
- **Сторы** — чистые редьюсеры событий с проверкой `lobbyId`/`matchId` (W9, W10). Навигация в одном модуле синхронизации маршрута. `router` в сторах не используется.
- **Ввод.** Один менеджер клавиатуры: контексты lobby/game/replay, фокус ввода, модификаторы, `event.repeat`. Один хелпер жестов с `touch-action: none` (W24–W28). Кнопка «назад» на Android идёт через `@capacitor/app` с подтверждением выхода из игры.
- **Рендер.** Базовый canvas-рендерер:
  - учитывает `devicePixelRatio`;
  - крутит rAF только пока есть анимация;
  - интерполирует по времени между двумя последними View (одна задержка тика);
  - анимации не зависят от частоты экрана;
  - тонированные спрайты кэшируются.
- **Локальный режим.** Кнопка «Играть» создаёт локальное лобби, «Онлайн-комната» — серверное. Если в онлайн-комнате на момент старта ты единственный человек и нет наблюдателей, клиент сам переносит игру в локальный режим с теми же настройками и ботами. Когда вкладка или приложение уходят в фон, локальная игра встаёт на паузу.
- **Pages**: `404.html` = копия `index.html` (SPA fallback). Генерация proto встроена в `predev`/`prebuild`.
- **Инструменты**: ESLint (flat, typescript-eslint, eslint-plugin-vue), Prettier, Vitest. Тесты покрывают транспорт (мок сокета: реконнект, resume, version-mismatch), сторы (гонки) и `MatchClient` с настоящим WASM в Node.
- **Бюджет размера** (проверка в CI): JS initial ≤ 120 КБ gzip, WASM ≤ 250 КБ gzip (`wasm-opt -Oz`). Порог уточняется после первого замера, но рост ловится автоматически.

### 4.8 Аутентификация (без БД)

- **Гость**: `Hello{guest{name}}`. Работает, только если сервер настроен с `allow_guests=true`; значение приходит клиенту в `Welcome` и через отдельный запрос `ServerInfo` до входа, и клиент прячет гостевой вход, если он выключен. У имени гостя есть пометка «гость». Id гостя (`u_…`) новый в каждой сессии.
- **Google**:
  - Веб: Google Identity Services (кнопка и One Tap) возвращают ID-токен.
  - Android: нативный Credential Manager с `serverClientId` = Web client ID.
  - Клиент шлёт `Hello{google{id_token}}`.
  - Сервер проверяет подпись RS256 по JWKS Google (ключи кэшируются по `Cache-Control`), `iss`, `aud == web client id` и `exp`.
  - Идентичность = `sub`, отображаемое имя = `name` из токена. Другим игрокам виден только id `g_…` — HMAC от `sub` на секрете сессий, одинаковый на всех устройствах; сам `sub` никуда не отправляется. Email не сохраняется и никому не показывается.
- **Имена не уникальны.** Игрок определяется по `Identity.id`, отображаемое имя — только подпись, у нескольких игроков оно может совпадать. Клиенты сравнивают игроков по id и сами различают тёзок на экране (аватар, «вы», «Имя · 2»).
- **Google Cloud**: проект `mini-games-514906`, consent screen в режиме Testing (вход только для тестовых пользователей; publish после страницы `/privacy` и переезда домена).
  - Web client ID (публичный): `996811598578-2dtc8gc90413c0qbtk87fhm84arqbrd3.apps.googleusercontent.com`.
  - Origins: `https://braintvsminigames.xyz`, `https://vladimirtyrin.github.io`, `http://localhost:5173`, `http://localhost:5000`.
  - Android-клиенты созданы: `mini-games-android-release` и `mini-games-android-debug`, package `xyz.braintvsminigames.app`. SHA-1 ключей из `.keys/` (папка в `.gitignore`): release `8E:13:88:BE:…:E6:E0`, debug `A3:63:5A:81:…:99:FB`. Debug-keystore общий для локальных и CI-сборок, поэтому Google-вход работает и в debug-APK.
  - Client secret не используется и в репозиторий не попадает.
- **Бот**: `Hello{bot{key}}`. Ключи задаются в конфиге или окружении сервера (`MG_BOT_KEYS=name:sha256(key),...`), сам ключ сервер не хранит. Бот виден как `name [bot]`. Это основа для будущих соревнований.
- **Сессия без БД**:
  - После успешного входа сервер выдаёт `session_token` = HMAC-SHA256 (секрет `MG_SESSION_SECRET` из окружения сервера) над `{kind, sub/name, exp=30d}`.
  - Клиент хранит токен (localStorage в вебе, Preferences в Android) и при следующих подключениях шлёт `Hello{session{token}}`. В Google не ходим, токен переживает рестарт сервера.
  - Отзыв токенов — только сменой секрета. Для текущего масштаба этого достаточно.
- **Ограничения среды**:
  - Google не разрешает origin по IP и по http, кроме localhost. Поэтому веб-вход через Google работает на `https://braintvsminigames.xyz`, на Pages и на localhost, а на `http://146.103.106.44` в вебе будет только гостевой вход.
  - Android-вход работает и против IP: проверка идёт на сервере, origin не нужен. Но до TLS токен идёт по сети в открытом виде. Для тестов это приемлемо: токен привязан к нашему `aud` и живёт 1 час.
- **Тесты**: проверка JWT на фикстурах со своим тестовым ключом (подделанная подпись, чужой `aud`, просроченный токен), HMAC-сессии, `allow_guests=false`, бот-ключи.

### 4.9 Эффективность сервера

Цель: сервер почти не ест ресурсов. Исключения — тяжёлые по природе вычисления вроде minimax, у них свой бюджет, и их можно улучшать отдельно.

- **Lockstep экономит трафик и CPU.** Сервер не сериализует полное состояние каждый тик. Кадр (чаще всего пустой, вида `{"tick":1042}`) кодируется **один раз** и рассылается всем получателям как общий `Bytes`, без копий на каждого клиента.
- **Ничего не крутится без дела.**
  - Пошаговые матчи событийные, таймера нет.
  - Real-time матч тикает только в состоянии `Running`; на паузе и после конца таймер остановлен.
  - Вместо периодических проходов по всем объектам — дедлайны внутри акторов (`sleep_until`).
  - Неактивные соединения закрываются по heartbeat.
- **Горячий путь без аллокаций.** Состояние игр лежит в плоских `Vec` и битовых сетках, без `HashMap` и строк; слоты имеют тип `u8`. Валидация команд не аллоцирует. На тик ничего не логируется.
- **Боты.**
  - Вычисления идут в `spawn_blocking` под семафором: одновременно не больше `N` вычислений, по умолчанию = число ядер.
  - Бюджет узлов на ход.
  - Улучшения minimax потом: iterative deepening, transposition table, упорядочивание ходов.
- **Рантайм.**
  - Число воркеров tokio настраивается, по умолчанию `min(ядра, 2)`.
  - Аллокатор mimalloc: стандартный musl-аллокатор медленный.
  - Release-профиль: `lto = "fat"`, `codegen-units = 1`, `strip = true`. `panic = unwind` сохраняем, чтобы паника в одном акторе не роняла весь процесс.
- **Статику отдаёт nginx** с долгим кэшем для хэшированных ассетов; в Rust-сервер идёт только `/ws`. Встроенная раздача статики в сервере остаётся для локального запуска и для `run_test.sh`.
- **Сжатие WS не используем.** У permessage-deflate состояние на каждое соединение весит сотни КБ, а кадры и так крошечные. Лог для catch-up отправляется компактно: только непустые кадры плюс финальный номер тика.
- **Измерение.** В `mg-bot-sdk` есть утилита нагрузки `loadgen`: N клиентов с матчами змейки и крестиков-ноликов. Базовые цифры фиксируются в `docs/architecture.md`. Ориентиры для 1 vCPU:
  - RSS в простое < 15 МБ;
  - 200 соединений и 50 real-time матчей < 10% CPU.

  Это ориентиры, а не гейт CI: при регрессии разбираемся.

## 5. Этапы (одна ветка `refactor/v2`, коммит или серия коммитов на этап)

У каждого этапа есть критерий готовности. Ветка не обязана быть деплоябельной между этапами 3 и 5, потому что протокол ломается целиком.

**Независимые ревью.** После этапов 2, 4 и 6 код проверяет отдельный ревьюер, у которого нет моего контекста и выводов: только код и требования (AGENTS.md, этот план). Найденное исправляется до перехода к следующему этапу, а исправления идут отдельными коммитами.

### Этап 0. Подготовка
- Установить инструменты:
  - `rustup target add wasm32-unknown-unknown`;
  - `wasm-bindgen-cli` (версия = версии крейта);
  - binaryen (`wasm-opt`);
  - JDK 21;
  - Android SDK cmdline-tools, platform и build-tools.

  cargo-ndk **не нужен**: нативного кода на Android нет.
- Ветка `refactor/v2`. `Cargo.lock` убрать из `.gitignore` и закоммитить. AGENTS.md, CLAUDE.md и `docs/` тоже убрать из игнора.
- Обновить зависимости. Rust: tokio 1.54, axum 0.8.9, prost 0.14.6, tower-http 0.7, clap 4.6, criterion 0.8.2. `rand` и `tonic` уходят из ядра; `rand` остаётся только на сервере для seed. npm: vite 8, vue-router 5, pinia 4, `@vitejs/plugin-vue` 6, vue-tsc 3, protobuf-es 2.17, tailwind 4.3.

- Каркас `ci.yml` на текущем коде: fmt, clippy и тесты зелёные.

**Готово, когда** CI зелёный на старом коде с новыми зависимостями, а инструменты стоят и проверены (`wasm-bindgen --version`, `sdkmanager --list`).

### Этап 1. `mg-core`
- Трейты `Game`/`Bot`, `Match<G>`, `CoreRng`, `StateHasher`, типы ошибок, `PlayerSpec`/`Slot`, `Clock`, `InputPolicy`, лог матча.

### Этап 2. Игры в ядре
Порядок от простых к сложным: puzzle2048 → numbers-match → tictactoe (+ боты) → snake (+ боты) → stack-attack.

Боты переводятся на бюджет узлов и детерминированный порядок кандидатов. Бенчмарк minimax переезжает в `mg-tictactoe`.

**Готово, когда** все 5 игр проходят conformance, а каждый пункт раздела 7 закрыт тестом.

**Готово, когда** round-trip JSON ↔ proto ↔ domain покрыт тестами для каждой игры, а `xtask new-game demo` даёт компилирующийся и зелёный по тестам проект. Demo потом удаляется.

### Этап 4. Сервер на ядре
- `mg-host` (авторитет: очередь ввода, `InputPolicy`, боты, пауза и бюджеты, голосование за дроп, кадры, хэши, лог).
- Переписанный сервер:
  - акторы (раздел 4.4);
  - идентичность и resume, аутентификация (гость, Google, бот, HMAC-сессии, `allow_guests`);
  - машина состояний лобби;
  - лимиты;
  - конфиг, `tracing`, shutdown;
  - ретрансляция реплеев.
- gRPC удаляется.
- Интеграционные тесты: сервер поднимается в тесте, скриптованные WS-клиенты на `mg-bot-sdk` проходят сценарии:
  - лобби (создать, войти, ready, старт, play-again);
  - матч с ботами до конца;

  - медленный клиент, который не читает (сервер остаётся отзывчивым для остальных: H1);
  - кик закрывает соединение, повторный вход разрешён;
  - мусор, огромный ввод и неверная версия протокола;
  - быстрый реконнект с тем же resume (M1);
  - гонка play-again (H7);
  - выход хоста посреди игры;
  - SIGTERM.

**Готово, когда** все сценарии зелёные, ни одного `unwrap`/`expect` на пути внешнего ввода нет (clippy-lint на крейте сервера, тестовый код исключён), а `loadgen` показывает цифры в пределах ориентиров из раздела 4.9.

## 6. Риски

| Риск | Митигация |
|---|---|
| Рассинхрон в lockstep из-за недетерминизма | Запреты в ядре на уровне lint и ревью; golden-хэши на x86 и WASM; `state_hash` раз в N тиков; авто-ресинк через `MatchCatchUp`; логирование `Desync` на сервере |
| Minimax на 20×20 тормозит в WASM на слабом телефоне | Бюджет узлов вместо глубины, Worker не блокирует UI, бюджет подбираем по бенчмарку на телефоне |
| Нет совместимой связки `pbjson` + prost 0.14 | Проверка на этапе 0; запасной вариант — `prost-reflect` с serde |
| TypeScript 7 несовместим с vue-tsc | Остаёмся на 5.x |
| Одна большая ветка долго живёт отдельно от `master` | `master` в это время не трогаем; если нужен хотфикс старой версии, делаем его в `master` и мержим в ветку |
| Старый WebView на Android 7 | WASM нужен Chrome 57+. WebView обновляется через Play, на minSdk 24 риск низкий; проверка на эмуляторе API 24 |
| Pages и сервер деплоятся независимо | `protocol_version` + сообщение «обновитесь» без бесконечного реконнекта; порядок выкатки из этапа 9 |

## 7. Changelog правил (что меняется для игроков)

**Snake**
- Ход одновременный. Лобовое столкновение или обмен клетками убивает обоих. В освобождающийся в этом тике хвост (свой или чужой) въехать можно, если та змейка не растёт.
- Исправлен въезд в собственный хвост, который портил состояние (S3).
- Бот Efficient при отсутствии еды переходит к безопасному случайному ходу, а не едет в стену (S5).
- Стартовые позиции не пересекаются при любом допустимом числе игроков (S6).
- Буфер ввода — 2 поворота на тик, второй применяется в следующем тике (S9).
- Если в партии были люди, игра заканчивается, когда не осталось живых людей. Если при этом живы несколько ботов, побеждают все выжившие боты (а не «ничья»).
- Вероятность еды задаётся целым числом в промилле.

**Stack Attack**
- Не больше одного действия рабочего за тик, остальные ставятся в очередь (до 3) (A3).
- Сдвинутая коробка падает, если под ней пусто (A1). После очистки линии гравитация проверяется заново (A9).
- Краны не роняют коробку в занятую клетку: второй кран ждёт (A2, коробки-призраки).
- Проверка потолка идёт после очистки линий (A6).
- Очки в событиях совпадают со счётом (A7). Время выживания считается в тиках (A10).
- Отключение игрока убирает только его рабочего, игра продолжается (A11).
- Новое правило — удар головой. Прыжок разбивает падающий ящик в клетке, куда поднимается голова (раньше он блокировал прыжок и в том же тике давил рабочего), и падающий ящик над ней, который в этом тике упал бы на голову; больше двух ящиков за прыжок не бывает. Лежащие ящики (в том числе сдвинутые) не разбиваются: такой ящик над головой по-прежнему блокирует прыжок. Ящик на кране недосягаем: кран отпускает ящик после прыжков, и отпущенный на голову ящик давит. Рабочего, который не прыгает (стоит или падает), ящик давит как раньше. Удар разрешается в фазе действий рабочих, в порядке мест, до кранов, гравитации и очистки линий: разбитый ящик не заполняет ряд, а если в один ящик прыгнули двое, засчитывается меньшему месту. Очков удар не даёт (иначе разбивать всё подряд выгоднее, чем собирать ряды); клиент получает событие `BoxBroken { box_id, cell, by_slot }`.

**TicTacToe**
- Режим «Host первым» действительно отдаёт первый ход хосту (T2). При случайном выборе первого игрока результат приходит как `WorldEvent`.
- Minimax:
  - терминальная оценка всегда доминирует над эвристикой (T4);
  - арифметика i64 с насыщением (T5);
  - бюджет узлов и детерминированный порядок кандидатов (T6, T7).
- Техническое поражение из-за дисконнекта получает свою причину `PLAYER_DISCONNECTED` (T8).

**Puzzle2048**
- Цель ограничена: степень двойки от 8 до 65536 (P3).
- Проигрыш показывается как поражение, а не как «Ничья» (W37).

**Numbers Match**
- Поиск доступной пары оптимизирован: один проход O(n) вместо O(n³) на каждый ход и hint (N3).
- Повторный запрос подсказки, пока прежняя ещё показана, отклоняется и не тратит подсказку (в legacy тратил впустую).
- Число добавлений (refill) настраивается: 0..=10, по умолчанию 5.

**Общее**
- Тип бота жёстко привязан к игре (H5).
- Настройки валидируются на любом пути (H3).
- Дисконнект обрабатывается по модели паузы с бюджетом (раздел 2).

- Клиентское предсказание своего ввода в онлайн-real-time (lockstep это позволяет).
- Google Play, PWA, iOS.
- Боты для Stack Attack.
